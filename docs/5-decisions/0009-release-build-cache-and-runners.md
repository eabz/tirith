# ADR-0009: Release builds cache dependencies and cross-compile Intel macOS on Apple Silicon

**Status:** Accepted, 2026-09-16

## Context

The `ci.yml` check job restores a `Swatinem/rust-cache` cache and finishes
in under a minute. The release workflow generated by cargo-dist had no
cache: every one of the eight target jobs compiled all 186 crates from
scratch in the `dist` profile. Release v0.1.2 took about 7.5 minutes wall
clock. The bound was the `x86_64-apple-darwin` job on the `macos-15-intel`
runner (6 minutes), roughly twice the time of the same build for
`aarch64-apple-darwin` on `macos-14`.

## Decision

Two settings in `dist-workspace.toml`, applied with `dist generate`:

- `cache-builds = true`. Every `build-local-artifacts` job now runs
  `swatinem/rust-cache@v2` keyed by target, so compiled dependencies are
  restored between releases and only the `tirith` crate and the LTO link
  are rebuilt.
- `github-custom-runners.x86_64-apple-darwin = "macos-14"`. The Apple
  toolchain cross-compiles both Mac targets, so the Intel binary is built
  on the Apple Silicon runner alongside the arm binary.

The target list and the `dist` profile (`lto = "thin"`,
`codegen-units = 1`, `strip = true`) are unchanged.

## Alternatives

- **Leave the cache off**, as cargo-dist recommends by default. The cache
  key includes `Cargo.toml` and `Cargo.lock`, which every version bump
  changes. rust-cache falls back to a prefix key in that case, so the
  previous release's dependency artifacts are still restored and cargo
  rebuilds only what changed. The occasional slow cache restore the dist
  docs warn about is cheaper than five minutes of cold compilation.
- **Drop targets** (`aarch64-pc-windows-msvc`, the musl pair). Would
  shorten the matrix but is a distribution decision, not a build-speed
  one; left for a separate ADR if wanted.
- **Raise `codegen-units`** in the `dist` profile. Would parallelise the
  leaf-crate build, which the cache cannot help with, at the cost of a
  larger binary. Rejected for now; small binaries are a project goal.

## Consequences

- Release builds for Linux and macOS should drop to about a minute once a
  cache exists; Windows improves less because its runner is slower overall.
- Eight cache entries per release count against the repository's 10 GB
  GitHub Actions cache limit. GitHub evicts least-recently-used entries, so
  no cleanup is needed.
- No Intel macOS runner is used any more. If a future dependency needs
  native Intel tooling at build time, remove the custom runner entry.
- `.github/workflows/release.yml` is still generated; edit
  `dist-workspace.toml` and rerun `dist generate`.
